# Обработка неполных пациентов: гейт, склейка сессий, UI для врача — Design Spec

**Дата:** 2026-08-06
**Ветка:** не определена
**Связано с:** KI-027 (эвристика скоринга серий), находки на `data/clinical_dicom/BO`

## Проблема

После фикса bare-"c" маркера контраста (BO) полнота датасета выросла с
81.4% до 88.0%, но 14 из 175 пациентов всё ещё неполные. Разбор показал
три независимых источника проблемы, требующих разных решений:

1. Часть неполных сессий на самом деле дополняют друг друга во времени
   (BO-195, BO-120 — один клинический визит, разбитый на 2 регистрации в
   РИС с разрывом в несколько дней/недель) — их можно безопасно
   объединить, но не автоматически вслепую (см. "Пример неправильного
   объединения" ниже).
2. Пайплайн сейчас не различает "неполного" пациента от полного нигде,
   кроме отчёта `01_reorganize_folders_incomplete_data.json`, который
   никто не читает дальше по цепочке — неполные пациенты доходят до
   сегментации, тратя время на конвертацию/предобработку впустую, и
   падают (или тихо дают мусорный результат) только в самом конце.
3. Врач, загружающий пачку пациентов через веб-интерфейс, никак не
   узнаёт, что часть из них не дошла до сегментации — эта информация
   сейчас существует только в файлах на бэкенде.

### Пример неправильного объединения (почему нельзя просто "разрыв ≤ N дней")

На `data/clinical_dicom/BO` проверены все 8 пар "сессия на соседнюю дату"
вручную по DICOM-тегам `Manufacturer`/`ManufacturerModelName`/
`PatientWeight`/`StudyDescription`:

| Пациент | Разрыв | Вендор/модель | Вес | Вердикт |
|---|---|---|---|---|
| BO-195 | 2 дня | Siemens→Siemens (Skyra→Aera) | 60→60 | безопасно |
| BO-120 | 6 дней | Siemens→Siemens (Skyra→Aera) | 70→65 | вероятно безопасно |
| BO-173 | 14 дней | Siemens→Siemens (Spectra→Skyra) | 102→80 (!) | пограничный, нужна ручная проверка |
| BO-142 | 4 дня | **Philips→Siemens** | 97→97 | НЕ объединять (разные учреждения) |
| BO-69 | 8 дней | **Philips→Siemens**, разный StudyDescription | 60→55 | НЕ объединять (внешний снимок) |
| BO-55, BO-82 | 6-14 дней | Philips ("ARCHIVIAZIONE DIGITALE PRECEDENTI") → Siemens | — | НЕ объединять (архивный снимок) |
| BO-155 | 15 дней | — | — | НЕ объединять (одна из сессий — фМРТ, другой тип исследования) |

Вывод: разрыв в датах — необходимый, но недостаточный сигнал. Надёжный
сигнал — совпадение вендора/модели сканера + согласованность веса
пациента + совпадающий тип исследования (StudyDescription). При
рассинхроне любого из этих сигналов сессии почти всегда представляют
разные реальные визиты (архивный снимок, другое учреждение, другой тип
обследования), и автосклейка исказит данные для сегментации/анализа.

## Архитектура: три независимых куска

```
A. Эвристика склейки сессий      — scripts/01_reorganize_folders.py, configs/
B. Гейт неполноты в пайплайне    — scripts/01_reorganize_folders.py, backend DB, pipeline_config.yaml
C. UI для врача                  — frontend/, backend API
```

Порядок реализации: **B → C → A** (B — фундамент для статуса, который
показывает C; A — самостоятельная фича, использует тот же UI-слот в C
для подтверждения).

## Кусок B: Гейт неполноты

### Где гейтить

Проверено по факту (`utils/config_loader.py:get_stage_input_dir`): вся
тяжёлая часть цепочки (`stage_04_quality`, `stage_05_preprocessing` →
`stage_06_segmentation` → `stage_07`/`stage_08`) читает вход либо
напрямую от `stage_03_convert`, либо транзитивно через неё. Гейтить
после `stage_03` было бы уже достаточно для всей тяжёлой цепочки, но
конвертация в NIfTI на этом же шаге — тоже трата времени на заведомо
неполного пациента.

**Решение: гейтить прямо в `01_reorganize_folders.py`.** К моменту
`SeriesDeduplicator.deduplicate_session()` (до `FileOrganizer.copy_series()`)
уже известно, какие модальности есть в сессии — оптимальная точка для
решения, копировать файлы в основное дерево или в сторонний "накопитель".

### Гранулярность: по сессии, не по пациенту

У одного пациента может быть одна полная сессия и одна неполная (пример:
BO-173 ses-001 полная, ses-002 — только t1c) — они гейтятся независимо.

### Физическое разделение

Вариант A (выбран): вложенная директория внутри основного дерева.

```
bids_organized/
├── sub-XXX/ses-YYY/anat/...       # полные сессии — как сейчас
└── _incomplete/
    └── sub-XXX/ses-YYY/anat/...   # неполные — та же структура
```

`stage_03` и всё ниже сканируют `input_dir.glob("sub-*")` — `_incomplete/`
структурно невидима, без единой правки в скриптах 03-08. Когда сессия
дособрана (см. кусок C), директория **переносится** (`shutil.move`) из
`_incomplete/sub-XXX/ses-YYY` в `sub-XXX/ses-YYY` — следующий обычный
прогон пайплайна подхватывает её как новый вход.

### Конфиг-флаг

Новый булев аргумент `--include-incomplete` в `01_reorganize_folders.py`
(по аналогии с существующими `--dry_run`/`--force`), пробрасывается из
`pipeline_config.yaml`:

```yaml
stages:
  stage_01_reorganize:
    args:
      include-incomplete: false   # true = старое поведение, гейт выключен
```

По умолчанию `false` (гейт активен). Если `true` — все сессии, включая
неполные, идут в основное дерево как раньше (флаг "прогнать всё, что
есть", запрошенный явно).

### Данные для UI: `dataset_mapping.json`

Единый файл для всех пациентов (не заводим третий файл). На уровне
сессии добавляется:

```json
"sessions": {
  "ses-001": {
    "original_date": "20201214",
    "status": "incomplete",
    "series": { "t1": {...}, "t2": {...}, "t2fl": {...} },
    "unrecognized_series": [
      {
        "original_path": "/path/to/some_weird_protocol",
        "series_description": "protocol_name | series_description",
        "slice_count": 24
      }
    ]
  }
}
```

`unrecognized_series` — серии, для которых `detect_modality()` вернул
`None` (`modality=None`, ветка `else` в `_process_one_patient_core`,
сейчас — только debug-лог, данные никуда не сохраняются). Это кандидаты
на ручную переразметку врачом. Серии, проигравшие дедупликацию (два
кандидата на t1) — **не включаем** (осознанное решение: минимум шума в
UI, эти случаи не требуют ручного вмешательства).

Технический нюанс для реализации: нераспознанные серии нужно прогонять
через ту же группировку по дате (`SessionGrouper.group_by_date`), что и
распознанные — иначе непонятно, к какой сессии их привязать.

### DB: статус-поле

`backend/schema.sql`, таблица `patient_registry` — новое поле уровня
сессии (сейчас в таблице нет ни одного статус-поля, только на уровне
`pipeline_runs`/`stage_executions`). Нужна отдельная таблица или
дополнительная колонка — детали (миграция, точный набор состояний:
`complete` / `incomplete` / `discarded`) прорабатываются на этапе плана
реализации.

## Кусок C: UI для врача

### Расположение

Внутри экрана конкретного запуска (там же, где `PipelineHistory`/
`StageProgress` сейчас показывают прогресс) — не отдельный глобальный
дашборд. Врач видит баннер/вкладку "N из M пациентов неполные" сразу
после завершения запуска, в контексте той самой пачки, которую он
загрузил.

### Экран деталей пациента (один экран, без отдельных подпотоков)

На карточке пациента:
- `missing` / `available` модальности (из отчёта о полноте)
- список `unrecognized_series` (путь, описание, число срезов) — по
  каждой кнопка "Пометить как [t1/t1c/t2/t2fl]"
- если пациент — участник пары-кандидата на склейку (кусок A): блок с
  конкретной причиной сомнения ("расхождение веса: 102кг → 80кг" /
  "другой вендор сканера" и т.п.) и кнопки "Объединить" / "Оставить
  раздельно"
- кнопка "Отбросить пациента" — помечает сессию как намеренно
  исключённую (не удаляет данные, просто убирает из списка "требует
  внимания")
- кнопка "Запустить обработку" — доступна, когда сессия(и) переведены в
  статус `complete` вручную

### Реквизация в пайплайн

Ручная кнопка, не автотриггер (осознанный выбор — врач может дособрать
несколько пациентов и запустить обработку одним батчем, а не N мелких
прогонов, что важно для gbm-seg/ms-seg микросервисов — меньше накладных
расходов на запуск).

Механизм переиспользует существующий `skip_existing: true` в
`pipeline_config.yaml` — кнопка просто триггерит обычный прогон пайплайна
над той же выходной директорией; `skip_existing` пропускает всех уже
обработанных, реально обрабатывается только дособранный пациент. Не
требует нового кода фильтрации по ID в scripts 03-08.

### Backend API (новые эндпоинты, точные контракты — на этапе плана)

- список неполных пациентов текущего запуска (источник — DB статус-поле
  из куска B)
- получить `unrecognized_series` конкретной сессии
- переразметить серию → модальность (перенос файла + обновление
  `dataset_mapping.json` + пересчёт статуса сессии + при необходимости
  перенос `_incomplete/` → основное дерево)
- отбросить пациента / сессию
- подтвердить/отклонить склейку (кусок A)
- запустить обработку (триггер обычного прогона, см. выше)

## Кусок A: Обобщение эвристики склейки сессий

### Применимость вне BO

Сигналы (`Manufacturer`, `ManufacturerModelName`, `PatientWeight`,
`StudyDescription`, разрыв дат) — стандартные DICOM-теги, не завязаны на
BO или итальянский язык (в отличие от текстовых контраст-маркеров
KM/MDC/bare-"c", которые были специфичны под конкретный источник данных).
Эвристика по построению датасет-агностична.

### Конфигурация per lesion_type

Порог "разрыва дат, ещё похожего на один визит" — **не одна глобальная
константа**. Для glioblastoma ~2-3 недели (нейронав-допконтраст перед
операцией — нормальная клиническая практика). Для multiple sclerosis
эвристика **выключена по умолчанию**: повторные МРТ через недели/месяцы
там — намеренно разные точки наблюдения (мониторинг эволюции очагов), а
не один визит, разбитый логистически. Автосклейка для MS может испортить
данные, а не улучшить.

```yaml
# ориентировочно, конфиг configs/series_scoring.yaml или отдельный файл
session_merge_heuristic:
  glioblastoma:
    enabled: true
    max_date_gap_days: 21
    weight_tolerance_percent: 15
    require_same_manufacturer: true
    require_same_model: false   # Skyra vs Aera — тот же вендор, другая модель, всё ещё ок
  multiple_sclerosis:
    enabled: false
```

### Что делает эвристика

Для каждой пары сессий одного пациента с непересекающимися (дополняющими
друг друга) наборами модальностей: если разрыв дат ≤ порога, вендор
сканера совпадает, вес пациента в пределах допуска — помечать как
"кандидат на объединение" (не объединять автоматически) и передавать в
UI куска C для подтверждения врачом.

## Открытые вопросы (для этапа плана реализации)

- Точная схема миграции БД для статус-поля (новая таблица vs колонка).
- Контракты backend API (пути, форматы запросов/ответов).
- Поведение при повторной ручной переразметке серии, которая уже была
  использована (перезапись vs явный конфликт).
- Нужна ли ревалидация DICOM-содержимого при переразметке (вдруг врач
  ошибочно пометит spine-серию как t1c) — вероятно, минимальная проверка
  (анатомический фильтр `anatomy_exclude` из `series_scoring.yaml` уже
  есть и может использоваться как предупреждение, не блокировка).
