# Обработка неполных пациентов: гейт, склейка сессий, UI для врача — Design Spec

**Дата:** 2026-08-06
**Ветка:** не определена
**Связано с:** KI-027 (эвристика скоринга серий), находки на `data/clinical_dicom/BO`

## Проблема

После фикса bare-"c" маркера контраста (BO) полнота датасета выросла с
81.4% до 88.0%, но 14 из 175 пациентов всё ещё неполные. Разбор показал
три независимых источника проблемы, требующих разных решений:

1. Часть неполных сессий на самом деле дополняют друг друга во времени
   (BO-195, BO-120 — один клинический визит, разбитый на 2 регистрации в
   РИС с разрывом в несколько дней/недель) — их можно безопасно
   объединить, но не автоматически вслепую (см. "Пример неправильного
   объединения" ниже).
2. Пайплайн сейчас не различает "неполного" пациента от полного нигде,
   кроме отчёта `01_reorganize_folders_incomplete_data.json`, который
   никто не читает дальше по цепочке — неполные пациенты доходят до
   сегментации, тратя время на конвертацию/предобработку впустую, и
   падают (или тихо дают мусорный результат) только в самом конце.
3. Врач, загружающий пачку пациентов через веб-интерфейс, никак не
   узнаёт, что часть из них не дошла до сегментации — эта информация
   сейчас существует только в файлах на бэкенде.

### Пример неправильного объединения (почему нельзя просто "разрыв ≤ N дней")

На `data/clinical_dicom/BO` проверены все 8 пар "сессия на соседнюю дату"
вручную по DICOM-тегам `Manufacturer`/`ManufacturerModelName`/
`PatientWeight`/`StudyDescription`:

| Пациент | Разрыв | Вендор/модель | Вес | Вердикт |
|---|---|---|---|---|
| BO-195 | 2 дня | Siemens→Siemens (Skyra→Aera) | 60→60 | безопасно |
| BO-120 | 6 дней | Siemens→Siemens (Skyra→Aera) | 70→65 | вероятно безопасно |
| BO-173 | 14 дней | Siemens→Siemens (Spectra→Skyra) | 102→80 (!) | пограничный, нужна ручная проверка |
| BO-142 | 4 дня | **Philips→Siemens** | 97→97 | НЕ объединять (разные учреждения) |
| BO-69 | 8 дней | **Philips→Siemens**, разный StudyDescription | 60→55 | НЕ объединять (внешний снимок) |
| BO-55, BO-82 | 6-14 дней | Philips ("ARCHIVIAZIONE DIGITALE PRECEDENTI") → Siemens | — | НЕ объединять (архивный снимок) |
| BO-155 | 15 дней | — | — | НЕ объединять (одна из сессий — фМРТ, другой тип исследования) |

Вывод: разрыв в датах — необходимый, но недостаточный сигнал. Надёжный
сигнал — совпадение вендора/модели сканера + согласованность веса
пациента + совпадающий тип исследования (StudyDescription). При
рассинхроне любого из этих сигналов сессии почти всегда представляют
разные реальные визиты (архивный снимок, другое учреждение, другой тип
обследования), и автосклейка исказит данные для сегментации/анализа.

## Архитектура: три независимых куска

```
A. Эвристика склейки сессий      — scripts/01_reorganize_folders.py, configs/
B. Гейт неполноты в пайплайне    — scripts/01_reorganize_folders.py, backend DB, pipeline_config.yaml
C. UI для врача                  — frontend/, backend API
```

Порядок реализации: **B → C → A** (B — фундамент для статуса, который
показывает C; A — самостоятельная фича, использует тот же UI-слот в C
для подтверждения).

## Кусок B: Гейт неполноты

### Где гейтить

Проверено по факту (`utils/config_loader.py:get_stage_input_dir`): вся
тяжёлая часть цепочки (`stage_04_quality`, `stage_05_preprocessing` →
`stage_06_segmentation` → `stage_07`/`stage_08`) читает вход либо
напрямую от `stage_03_convert`, либо транзитивно через неё. Гейтить
после `stage_03` было бы уже достаточно для всей тяжёлой цепочки, но
конвертация в NIfTI на этом же шаге — тоже трата времени на заведомо
неполного пациента.

**Решение: гейтить прямо в `01_reorganize_folders.py`.** К моменту
`SeriesDeduplicator.deduplicate_session()` (до `FileOrganizer.copy_series()`)
уже известно, какие модальности есть в сессии — оптимальная точка для
решения, копировать файлы в основное дерево или в сторонний "накопитель".

### Гранулярность: по сессии, не по пациенту

У одного пациента может быть одна полная сессия и одна неполная (пример:
BO-173 ses-001 полная, ses-002 — только t1c) — они гейтятся независимо.

### Физическое разделение

Вариант A (выбран): вложенная директория внутри основного дерева.

```
bids_organized/
├── sub-XXX/ses-YYY/anat/...       # полные сессии — как сейчас
└── _incomplete/
    └── sub-XXX/ses-YYY/anat/...   # неполные — та же структура
```

`stage_03` и всё ниже сканируют `input_dir.glob("sub-*")` — `_incomplete/`
структурно невидима, без единой правки в скриптах 03-08. Когда сессия
дособрана (см. кусок C), директория **переносится** (`shutil.move`) из
`_incomplete/sub-XXX/ses-YYY` в `sub-XXX/ses-YYY` — следующий обычный
прогон пайплайна подхватывает её как новый вход.

### Конфиг-флаг

Новый булев аргумент `--include-incomplete` в `01_reorganize_folders.py`
(по аналогии с существующими `--dry_run`/`--force`), пробрасывается из
`pipeline_config.yaml`:

```yaml
stages:
  stage_01_reorganize:
    args:
      include-incomplete: false   # true = старое поведение, гейт выключен
```

По умолчанию `false` (гейт активен). Если `true` — все сессии, включая
неполные, идут в основное дерево как раньше (флаг "прогнать всё, что
есть", запрошенный явно).

### Данные для UI: `dataset_mapping.json`

Единый файл для всех пациентов (не заводим третий файл). На уровне
сессии добавляется:

```json
"sessions": {
  "ses-001": {
    "original_date": "20201214",
    "status": "incomplete",
    "series": { "t1": {...}, "t2": {...}, "t2fl": {...} },
    "excluded_series": [
      {
        "original_path": "/path/to/some_weird_protocol",
        "series_description": "protocol_name | series_description",
        "slice_count": 24,
        "detected_modality": null,
        "reason": "unrecognized"
      },
      {
        "original_path": "/path/to/duplicate_t1",
        "series_description": "sT1W_3D_TFE",
        "slice_count": 200,
        "detected_modality": "t1",
        "reason": "lost_deduplication"
      }
    ]
  }
}
```

**Обновлено после реального прогона на `data/clinical_dicom/BO/test`**
(`BO-68`): исходное решение "серии, проигравшие дедупликацию — не
включаем" оказалось слишком узким. Реальный случай — два одинаковых `T1`
(повторная съёмка, ни на одном нет контрастного маркера), один выбран
дедупликацией, второй теряется безвозвратно. Врач не может увидеть,
что был второй кандидат, и тем более не может подменить им уже выбранный
t1, если тот, по его мнению, хуже. Смысл всей фичи — не "пайплайн сам
решает, чего не хватает", а "врач видит всё, что не попало в финальный
набор, и управляет этим сам" — значит, дедупликация не должна быть
безвозвратной.

`unrecognized_series` переименовано в **`excluded_series`** и объединяет
обе причины исключения:
- `reason: "unrecognized"` — `detect_modality()` вернул `None`
  (`modality=None`, ветка `else` в `_process_one_patient_core`).
  `detected_modality: null`.
- `reason: "lost_deduplication"` — серия была классифицирована, но
  `SeriesDeduplicator._select_best_series()` выбрал другого кандидата на
  ту же модальность. `detected_modality` — во что её распознал алгоритм.

Врач не ограничен `detected_modality` при переразметке (кусок C) — может
назначить любую исключённую серию на любую из 4 модальностей, не только
на ту, что предложил алгоритм; `detected_modality` — только подсказка в
UI.

Технический нюанс для реализации: и нераспознанные, и проигравшие
дедупликацию серии нужно прогонять через ту же группировку по дате
(`SessionGrouper.group_by_date`), что и победившие — иначе непонятно, к
какой сессии их привязать. Проигравшие дедупликацию уже находятся внутри
`deduplicate_session()`, которая сейчас их просто отбрасывает
(`SeriesDeduplicator.deduplicate_session`, `scripts/01_reorganize_folders.py`)
— нужно сохранять их в `SessionInfo.excluded_series` вместо отбрасывания.

**Обратная совместимость:** не нужна. `dataset_mapping.json` от прогонов
до этого изменения не содержит `excluded_series` вообще (только старое
`unrecognized_series` без дедуп-кандидатов) — старые прогоны нужно
пересчитать (`--force`), отдельный read-compat шим не пишем.

### DB: статус-поле

Отменено — см. "Backend API" в куске C ниже: `patient_registry`
заполняется только после полного завершения прогона, на нужном этапе там
для неполных пациентов ничего нет. Статус читается/пишется напрямую в
`dataset_mapping.json`, без БД и миграций.

## Кусок C: UI для врача

**Стек:** React 19 + Ant Design v6 (`frontend/`), без роутинга — навигация
через `useState` + `Tabs`/`Modal`. Существующий идиоматичный паттерн для
"экрана результатов конкретного запуска" — не отдельная вкладка/маршрут, а
**модалка, открываемая кнопкой действия** (см. `QualityReport.jsx`,
`ClinicalReport.jsx`, `NIfTIViewer.jsx` — все триггерятся из `PipelineHistory`
и `ProgressMonitor`, состояние видимости живёт в `App.jsx`). Новый экран
следует этому же паттерну, не изобретает свой.

### Расположение и точка входа

Кнопка "Неполные пациенты" появляется в **двух** местах, оба уже
показывают действия, привязанные к конкретному этапу:

- **`ProgressMonitor.jsx`** (активный запуск) — сразу после завершения
  **этапа 1**, не дожидаясь всего прогона. Технически — тот же паттерн,
  которым уже гейтятся `onShowQualityReport` (этап 3) и
  `onShowClinicalReport` (этапы 6/7) в `StageProgress.jsx`: кнопка активна,
  когда `stageData.stage_number === 1 && stageData.status === 'completed'`.
  Врач может начать разбирать проблемы, пока остальные пациенты ещё
  обрабатываются на поздних этапах — не нужно ждать часы до конца прогона.
- **`PipelineHistory.jsx`** (история запусков) — в колонке "Действия",
  как остальные кнопки там, без гейта по этапу (запуск уже завершён).

### Два уровня модалок

**Модалка 1 — список сессий, требующих внимания** (новый компонент
`IncompletePatients.jsx`, аналог `ValidationPanel.jsx`'s таблицы):
- `Table`: Пациент (`original_id`), Дата, Статус-тег (`incomplete` /
  `complete` — для complete-сессий тег означает "есть альтернативные
  кандидаты", не "не хватает модальности"), доступные модальности как
  `Tag`ов ряд, клик по строке → Модалка 2.
- Кнопка "Запустить обработку" (requeue) сверху, на весь запуск, а не
  на сессию — доступна не только когда что-то дособрано, полагается на
  `skip_existing` (см. "Реквизация" ниже).

**Модалка 2 — детали одной сессии:**
- Модальности как теги: зелёный — есть (`available`, из ответа API),
  серый — не хватает (`missing`, вычисляется **на бэкенде** — см.
  примечание ниже, не дублируется в JS).
- Список `excluded_series` (путь, описание, число срезов, подсказка
  `detected_modality`/`reason` — "алгоритм распознал как t1, но выбрал
  другую копию") — по каждой строке `Select` с модальностями (по
  умолчанию выбран `detected_modality`, если он есть) + кнопка
  "Назначить". Без ограничения выбора по `detected_modality` — свобода
  выбора любой из требуемых модальностей.
  - Если целевой слот уже занят другой серией — назначение оборачивается
    в `Popconfirm` ("Эта модальность уже заполнена другой серией —
    заменить?"), по аналогии с остальными необратимыми действиями в
    кодовой базе (`ValidationActions.jsx`). Если слот пуст — обычная
    кнопка без подтверждения. И тот, и другой случай в API — один и тот
    же вызов `relabel`; старая серия при замене возвращается в
    `excluded_series`, а не пропадает.
- Кнопка "Отбросить сессию" — тоже `Popconfirm`, помечает сессию как
  намеренно исключённую (не удаляет данные, просто убирает из списка
  "требует внимания").
- Блок для пары-кандидата на склейку (кусок A) — **не входит в эту
  реализацию**: кусок A ещё не реализован на бэкенде (только эвристика
  описана в спеке), эндпоинта подтверждения/отклонения склейки нет.
  Добавится отдельным заходом, когда до куска A дойдёт очередь.

**Примечание про `missing`:** ответ `GET /api/incomplete-patients/{run_id}`
сейчас отдаёт только `available` (что есть), не `missing` (чего не
хватает) — посчитать это на фронте означало бы дублировать в JS знание о
том, какие модальности требуются для каждого `lesion_type` (4 для
glioblastoma, 3 для MS), которое уже есть в `configs/lesion_types.yaml` и
`utils.config_loader.load_lesion_type_config`. Вместо дублирования —
маленький патч бэкенда: `get_incomplete_patients()` начинает принимать
`lesion_type` (тот же паттерн, что уже есть в `relabel_series()`) и
добавляет `missing: List[str]` в каждую сессию ответа.

### Реквизация в пайплайн

Ручная кнопка, не автотриггер (осознанный выбор — врач может дособрать
несколько пациентов и запустить обработку одним батчем, а не N мелких
прогонов, что важно для gbm-seg/ms-seg микросервисов — меньше накладных
расходов на запуск).

Механизм переиспользует существующий `skip_existing: true` в
`pipeline_config.yaml` — кнопка просто триггерит обычный прогон пайплайна
над той же выходной директорией; `skip_existing` пропускает всех уже
обработанных, реально обрабатывается только дособранный пациент. Не
требует нового кода фильтрации по ID в scripts 03-08.

### Backend API

**Без БД.** `patient_registry` (единственная таблица, теоретически
подходящая под статус пациента) заполняется только `kappa_uploader.py`,
который срабатывает исключительно после **полного завершения** прогона —
на момент "только что прошёл этап 01" в БД для неполных пациентов ничего
нет, часть из них туда вообще не дойдёт (их держит гейт куска B). Статус
уже лежит там, где он реально появляется — в `dataset_mapping.json`
(кусок B). Backend API читает и пишет этот файл напрямую, без
дублирующего источника правды и без миграции.

**Общий модуль для переразметки.** `FileOrganizer.copy_series()` из
`01_reorganize_folders.py` (копирование + анонимизация DICOM) выносится в
`utils/dicom_file_ops.py` — и `01_reorganize_folders.py`, и backend API
вызывают одну и ту же функцию, без дублирования copy/anonymize-логики.

Эндпоинты:

- `GET /api/incomplete-patients/{run_id}` — находит `output_path` и
  `lesion_type` через `pipeline_runs`, читает `dataset_mapping.json`,
  отдаёт сессии, которым нужно внимание врача: всё `status == "incomplete"`,
  плюс `status == "complete"` сессии, у которых непустой `excluded_series`
  (есть что пересмотреть — например, проигравший дедупликацию кандидат).
  `complete` без `excluded_series` и `discarded` — не отдаются. Каждая
  сессия несёт `available` (что есть) и `missing` (чего не хватает,
  считается на бэкенде через `load_lesion_type_config(lesion_type)` —
  фронт не дублирует это знание) и `excluded_series`. Один эндпоинт на
  весь экран — отдельного "получить детали одной сессии" не нужно (решение
  куска C: два уровня модалок читают один и тот же ответ целиком).
- `POST /api/incomplete-patients/{run_id}/{patient_id}/{session_id}/relabel`
  — тело `{original_path, modality}`. Через `utils/dicom_file_ops.py`
  копирует+анонимизирует размеченную серию в правильное место BIDS,
  обновляет `dataset_mapping.json` (серия переезжает из
  `excluded_series` в `series[modality]`; если слот `modality` уже занят
  — прежняя серия возвращается в `excluded_series`, не теряется),
  пересчитывает `status`; если сессия стала полной — физически переносит
  директорию из `_incomplete/` в основное дерево.
- `POST /api/incomplete-patients/{run_id}/{patient_id}/{session_id}/discard`
  — выставляет `status: "discarded"` в `dataset_mapping.json` (новое
  значение статуса, наряду с `complete`/`incomplete`).
- `POST /api/pipeline-runs/{run_id}/requeue` — вызывает уже существующие
  `PipelineManager.create_runtime_config()` + `start_pipeline()` на тех же
  `input_path`/`output_path`, что и исходный запуск. `skip_existing: true`
  уже часть базового конфига — ничего изобретать не нужно, только новый
  эндпоинт, дёргающий существующий механизм.
- Подтверждение/отклонение склейки (кусок A) — эндпоинт того же типа, что
  `relabel`/`discard`; проектируется вместе с куском A, когда до него
  дойдёт очередь.

## Кусок A: Обобщение эвристики склейки сессий

### Применимость вне BO

Сигналы (`Manufacturer`, `ManufacturerModelName`, `PatientWeight`,
`StudyDescription`, разрыв дат) — стандартные DICOM-теги, не завязаны на
BO или итальянский язык (в отличие от текстовых контраст-маркеров
KM/MDC/bare-"c", которые были специфичны под конкретный источник данных).
Эвристика по построению датасет-агностична.

### Конфигурация per lesion_type

Порог "разрыва дат, ещё похожего на один визит" — **не одна глобальная
константа**. Для glioblastoma ~2-3 недели (нейронав-допконтраст перед
операцией — нормальная клиническая практика). Для multiple sclerosis
эвристика **выключена по умолчанию**: повторные МРТ через недели/месяцы
там — намеренно разные точки наблюдения (мониторинг эволюции очагов), а
не один визит, разбитый логистически. Автосклейка для MS может испортить
данные, а не улучшить.

```yaml
# ориентировочно, конфиг configs/series_scoring.yaml или отдельный файл
session_merge_heuristic:
  glioblastoma:
    enabled: true
    max_date_gap_days: 21
    weight_tolerance_percent: 15
    require_same_manufacturer: true
    require_same_model: false   # Skyra vs Aera — тот же вендор, другая модель, всё ещё ок
  multiple_sclerosis:
    enabled: false
```

### Что делает эвристика

Для каждой пары сессий одного пациента с непересекающимися (дополняющими
друг друга) наборами модальностей: если разрыв дат ≤ порога, вендор
сканера совпадает, вес пациента в пределах допуска — помечать как
"кандидат на объединение" (не объединять автоматически) и передавать в
UI куска C для подтверждения врачом.

## Открытые вопросы (для этапа плана реализации)

- Поведение при повторной ручной переразметке серии, которая уже была
  использована (перезапись vs явный конфликт).
- Нужна ли ревалидация DICOM-содержимого при переразметке (вдруг врач
  ошибочно пометит spine-серию как t1c) — вероятно, минимальная проверка
  (анатомический фильтр `anatomy_exclude` из `series_scoring.yaml` уже
  есть и может использоваться как предупреждение, не блокировка).
- Найдено финальным ревью куска B: `check_patient_exists()` в
  `01_reorganize_folders.py` не проверяет `_incomplete/`, поэтому пациент,
  у которого **все** сессии неполные, никогда не создаёт директорию в
  основном дереве и каждый повторный прогон стадии 01 обрабатывает его
  заново (не деструктивно, но не даёт `skip_existing` отличить "ещё не
  трогали" от "уже пытались, всё ещё неполный"). Для куска C это означает:
  реквизация (`requeue`) должна ориентироваться на статус в
  `dataset_mapping.json`, а не только полагаться на факт существования
  директории в основном дереве.
