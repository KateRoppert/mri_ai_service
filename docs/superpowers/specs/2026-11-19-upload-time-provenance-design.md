# Происхождение данных фиксируется в момент выгрузки, а не в момент прогона

**Дата:** 19.11.2026
**Ветка:** `fix/upload-time-provenance`
**Закрывает:** KI-084 (реестр: одна строка на исследование), KI-085
(`preprocessing_id` считается при выгрузке; `register_version` не вызывается)

## 1. Одна причина, два дефекта

Выгрузка в Kappa записывает не то, что было верно, когда прогон шёл, а то,
что верно в момент выгрузки. Между этими моментами могут пройти дни:
отложенная доставка срабатывает при недоступности Kappa, при офлайн-режиме и
при догрузке старых прогонов (ноябрьская догрузка `test500` в датасет 375 шла
через два месяца после прогона).

Из этого выросли два независимо наблюдаемых дефекта.

**KI-085.** `KappaUploader.__init__` вызывает
`compute_preprocessing_id(preprocessing_config_path)`
([`backend/kappa_uploader.py:105`]), а путь ему дают фиксированный — живой
`configs/preprocessing_config.yaml`
([`backend/kappa_delivery_worker.py:63`], [`backend/pipeline_monitor.py:154`]).
Файл читается в момент выгрузки, поэтому в `patient_registry.preprocessing_id`
попадает хэш сегодняшних настроек, а не тех, с которыми считали.

**KI-084.** `patient_registry` хранит **одну строку на `study_hash`** —
ограничение зашито уникальным индексом `ix_patient_registry_study_hash`, а
`register_patient` при повторной регистрации перезаписывает `kappa_dataset_id`
и `kappa_entity_id` ([`backend/patient_registry.py:118-136`]). Поэтому одно и
то же исследование нельзя знать в двух датасетах: выгрузка в новый датасет
стирает память о том, где оно лежало раньше.

## 2. Почему это не косметика

### 2.1. `preprocessing_id` выбирает датасет

Тот же идентификатор участвует в разрешении датасета:
[`backend/numbering.py:73`] считает его при старте прогона и отдаёт в
`resolve_or_create`, где он становится частью ключа
`get_dataset_id(user_id, lesion_type, preprocessing_id)`
([`backend/kappa_dataset_resolver.py:49`]).

`dataset_id` при старте закрепляют **именно для того**, чтобы правка конфига в
полёте не растащила нумерацию и выгрузку по двум датасетам — это записано в
докстринге `_resolve_dataset_id`:

> Prefers the one fixed at run start (backend/numbering.py) — resolving again
> here could pick a different dataset if `current` moved in
> configs/kappa_datasets.yaml while the run was in flight, splitting numbering
> and upload across two datasets.

Половину с `dataset_id` закрепили, половину с `preprocessing_id` — нет. Защита
держится только потому, что при непустом `dataset_id` до повторного
разрешения дело не доходит; для прогонов без сессии Kappa (`dataset_id = NULL`)
она не работает вовсе.

### 2.2. По `preprocessing_id` нельзя узнать настройки

`register_version` ([`backend/preprocessing_version.py:76`]) пишет историю
версий, но **в продакшене не вызывается нигде** — только в тестах
(`git grep register_version` даёт определение и `test_preprocessing_version.py`).

Измеренное состояние на 19.11.2026:

| где | идентификаторы |
|---|---|
| `configs/preprocessing_versions.json` | `1e2b93ad` (создан 02.04.2026), всего одна запись |
| живой `configs/preprocessing_config.yaml` | `68328743` |
| `configs/kappa_datasets.yaml` | `3a183dc7`, `1e2b93ad`, `1099b9cd` |

То есть у трёх из четырёх когда-либо использованных идентификаторов за ними не
стоит ничего: восстановить по хэшу, что именно делали с данными, невозможно.
Хэш как версия работает только в паре с хранилищем, которое по хэшу отдаёт
содержимое.

## 3. Что уже готово к правке, а что нет

Радиус KI-084 оказался меньше, чем выглядел.

**Готово и менять не нужно:**

- Продакшен-поиски идут через `find_by_bids_id(bids_id, {dataset_id})`, который
  уже фильтрует по датасету и уже включает строки с `NULL`
  ([`backend/patient_registry.py:197-222`]). Места, где из записей берут первую
  с непустым `kappa_entity_id` ([`backend/app.py:958`], [`backend/app.py:3168`],
  [`backend/kappa_delivery.py:351`]), работают по уже отфильтрованному набору и
  пропускают строки без `kappa_entity_id`. После правки они становятся
  **точнее**, а не ломаются: сейчас они не находят строку для нужного датасета
  просто потому, что строка одна.
- `find_by_kappa_entity` ищет по UUID сущности, который глобально уникален.
- Колонка `patient_registry.preprocessing_id` уже существует.
- В `backend/database.py` есть готовый шаблон добавочной миграции колонки
  (`_migrate_add_kappa_dataset_id`, `database.py:401`).

**Требует правки:**

- Уникальный индекс `ix_patient_registry_study_hash`.
- Логика upsert в `register_patient`.
- `find_by_study_hash` — становится неоднозначной. Используется **только в
  тестах**, продакшен-потребителей нет.
- Модель `registry_models.PatientRegistry` (`unique=True` на `study_hash`).
- `pipeline_runs` — новая колонка `preprocessing_id`.

## 4. Решение, часть A: закрепить `preprocessing_id` при старте

По образцу `kappa_dataset_id`, вплоть до способа деградации на старых данных.

1. **Колонка.** `pipeline_runs.preprocessing_id VARCHAR NULL`, добавочная
   миграция по образцу `_migrate_add_kappa_dataset_id`. `NULL` означает
   «прогон старше этой правки».
2. **Запись при старте.** `numbering.scope_for_run` уже считает идентификатор
   там, где нужно (строка 73), и выбрасывает его. Сейчас функция возвращает
   тройку `(scope, dataset_id, note)`; она становится четвёркой
   `(scope, dataset_id, preprocessing_id, note)`, и значение пишется в строку
   прогона через `create_pipeline_run(..., preprocessing_id=...)`
   ([`database.py:140`]) — туда же, куда уже пишется `kappa_dataset_id`.
   Вызывающих у `scope_for_run` немного, все в `backend/`; распаковку тройки
   нужно поправить у каждого.
   Для прогонов без сессии Kappa (ветка `offline()`) идентификатор считается
   из того же живого конфига — на старте он всё равно верен, в отличие от
   момента выгрузки.
3. **Чтение при выгрузке.** `KappaUploader.__init__` получает необязательный
   `preprocessing_id`; `compute_preprocessing_id(path)` вызывается **только
   когда он None**. Докстринг повторяет логику `_resolve_dataset_id`:
   пересчёт здесь может дать другой ответ, чем при старте.
   `build_uploader` ([`kappa_delivery_worker.py:56`]) и
   `PipelineMonitor._create_kappa_uploader` передают сохранённое значение.
4. **Регистрация версии.** `register_version` вызывается при старте прогона,
   в том же месте, где идентификатор закрепляется. Так идентификатор всегда
   разрешим в настройки.

### 4.1. Где хранить историю версий

`register_version` сейчас пишет в `configs/preprocessing_versions.json` — файл
**отслеживается гитом**, а `configs/` смонтирован в контейнер на запись.
Вызывать его из приложения означает, что при каждой правке конфига контейнер
делает рабочую копию грязной. Это уже болезненная тема: `kappa_datasets.yaml`,
`pipeline_config.yaml` и `preprocessing_config.yaml` держатся грязными
намеренно, и добавлять к ним четвёртый автогенерируемый файл нельзя.

**Решение:** история версий переезжает в таблицу
`preprocessing_versions (preprocessing_id TEXT PRIMARY KEY, created_at
DATETIME, config_json TEXT)` в `backend/data/brain_lesion.db` — это volume, он
машинно-локален и вне гита, как и остальное состояние прогонов.
`get_version_config` сначала смотрит в таблицу, затем — в старый JSON, чтобы
единственная унаследованная запись `1e2b93ad` осталась читаемой. Сам JSON
больше не пишется.

## 5. Решение, часть B: ключ реестра

Ключ становится парой «исследование + датасет»: одно исследование может
присутствовать в нескольких датасетах Kappa, и это нормальная ситуация, а не
ошибка (`CLAUDE.md`: «Один и тот же человек в двух датасетах — это два разных
номера»).

### 5.1. Уникальность с учётом NULL

`kappa_dataset_id` бывает пустым: `session_registry` пишет строки при
завершении прогона, то есть **до любой выгрузки**, и для CLI-прогонов и
прогонов без сессии Kappa датасета там нет вовсе
([`backend/session_registry.py:40-47`]). В SQLite `UNIQUE` считает NULL
различными значениями, поэтому наивный `UNIQUE(study_hash, kappa_dataset_id)`
разрешил бы сколько угодно недоставленных дублей одного исследования.

Поэтому индекс по выражению (SQLite на машинах — 3.50.3, выражения
поддерживаются с 3.9):

```sql
DROP INDEX ix_patient_registry_study_hash;
CREATE UNIQUE INDEX ix_patient_registry_study_dataset
    ON patient_registry (study_hash, COALESCE(kappa_dataset_id, 0));
```

`0` — не идентификатор датасета Kappa (они положительные), поэтому он
безопасен как значение «ещё не доставлено».

### 5.2. Правило upsert

Это ядро правки. Сейчас `session_registry` и `KappaUploader` намеренно
опираются на то, что ключ — один `study_hash`: первая сторона создаёт строку
без идентификаторов Kappa, вторая её дополняет. Это из докстринга
`session_registry`:

> the uploader's own register_patient call later fills in `kappa_entity_id` —
> it upserts by study_hash, which both sides compute through session_identity
> precisely so they land on the same row.

Передачу между ними нужно сохранить. `register_patient(study_hash,
kappa_dataset_id, ...)` ищет строку так:

1. Точное совпадение `(study_hash, kappa_dataset_id)` — обновить её.
2. Иначе, если `kappa_dataset_id` задан: строка `(study_hash, NULL)` — это та
   самая, которую оставил `session_registry` в ожидании доставки. **Присвоить**
   её: записать `kappa_dataset_id` и `kappa_entity_id`. Так передача
   «локальная запись → выгрузка» продолжает работать.
3. Иначе — создать новую строку.

Следствия, которые это даёт правильно:

- исследование, доставленное в 347, а потом в 375, получает **две** строки, и
  обе указывают на свою сущность;
- повторная выгрузка в тот же датасет по-прежнему обновляет одну строку;
- `session_registry` для прогона без Kappa создаёт ровно одну строку с NULL и
  не плодит дубли при повторных завершениях.

Случай, который остаётся допустимым и описан явно: у исследования есть строка
для 347 и строка с NULL (прогон переделали без сессии Kappa). Датасет-зависимый
поиск вернёт обе, но строку с NULL отбросят проверки на непустой
`kappa_entity_id`, которые в этих местах уже стоят.

### 5.3. `find_by_study_hash`

Получает необязательный `dataset_id` и возвращает строку для этого датасета;
без него — список всех строк исследования. Продакшен-потребителей нет,
правятся только тесты.

## 6. Миграция существующих данных

Данных мало и они однозначны: на баргузине 323 строки, дублей по
`(study_hash, COALESCE(kappa_dataset_id, 0))` — **ноль** (проверено
19.11.2026). Миграция — только пересоздание индекса, строки не меняются:

1. копия БД (как в `utils/bids_allocation_migration.py`);
2. `DROP INDEX ix_patient_registry_study_hash`;
3. `CREATE UNIQUE INDEX ix_patient_registry_study_dataset ...`;
4. если шаг 3 упал на конфликте — миграция не применяется, печатаются
   конфликтующие пары. Автоматически сливать строки нельзя: это клинические
   данные, и решение «какая из двух правильная» не наше.

Миграция добавочная и идемпотентная, как остальные в `database.py`: проверяет
наличие индекса по имени.

### 6.1. Восстановление 319 строк после догрузки `test500`

Ноябрьская догрузка в датасет 375 перенаправила на него строки 319
исследований, которые до этого указывали на 347 и 348. Их прежние значения
сняты в дамп `backend/data/registry-before-375-*.json` **перед** записью.

Дефект при этом наблюдался напрямую, а не выводился из кода. Распределение
строк по датасетам до выгрузки и в середине неё (19.11.2026):

| датасет | до выгрузки | в середине |
|---|---|---|
| 347 | 205 | 167 |
| 348 | 114 | 79 |
| 375 | 0 | 74 |

Общее число строк не изменилось (323): записи не добавлялись, а
переписывались — ровно то, что делает `register_patient` при совпадении
`study_hash`.

После правки эти строки восстанавливаются: для каждой записи дампа создаётся
строка `(study_hash, прежний dataset_id)` с прежним `kappa_entity_id`, а строка,
указывающая на 375, остаётся как есть. Это разовая операция, отдельным
скриптом, не частью миграции схемы: она зависит от конкретного дампа и должна
запускаться осознанно.

## 7. Тесты

Новые, рядом с правимым кодом (`backend/test_*.py`):

**Часть A:**
- идентификатор, закреплённый при старте, попадает в строку прогона;
- `KappaUploader` с переданным `preprocessing_id` **не** читает файл конфига
  (подменить путь на несуществующий — конструктор обязан пройти);
- `KappaUploader` без него считает из файла (путь деградации для старых
  прогонов);
- выгрузка прогона, стартовавшего при одном конфиге и выгружаемого при
  другом, пишет в реестр идентификатор **старта** — регрессионный тест на
  сам дефект;
- `register_version` при старте делает идентификатор разрешимым:
  `get_version_config(id)` отдаёт настройки;
- `get_version_config` читает унаследованную запись `1e2b93ad` из JSON.

**Часть B:**
- одно исследование в двух датасетах даёт две строки, у каждой свой
  `kappa_entity_id`;
- повторная регистрация в том же датасете обновляет строку, а не создаёт;
- присвоение строки с NULL: `session_registry` создал, выгрузка дополнила, в
  итоге одна строка с датасетом;
- два завершения прогона без Kappa не создают двух строк с NULL (проверка
  уникальности с `COALESCE`);
- миграция индекса идемпотентна;
- миграция отказывается и ничего не меняет при конфликте.

Тесты пишут только в `tmp_path` (через `backend/conftest.py`), в рабочие
конфиги и в корень репозитория — никогда.

## 8. Чего мы не делаем (YAGNI)

- **Не** делаем идентификаторы сущностей датасет-зависимыми: UUID уже
  глобально уникален.
- **Не** переносим в БД старый JSON целиком: читаем его как резервный
  источник, записей там одна.
- **Не** восстанавливаем 319 строк автоматически в миграции — отдельный
  осознанный запуск.
- **Не** трогаем `preprocessing_id` в `kappa_datasets.yaml`: ключи `*:current`
  уже работают как аварийный выход, когда хэш живого конфига не совпадает ни
  с одним прописанным.
- **Не** вводим версионирование самих масок: это уже есть в `mask_versions`.

## 9. Журнал решений

| Решение | Почему |
|---|---|
| Закреплять `preprocessing_id` при старте, а не снимок конфига целиком | Снимок уже делается для остановленных прогонов (`app.py:659`); для всех прогонов это дубль данных. Идентификатор плюс таблица версий дают то же самое без копий файлов. |
| `NULL` = «прогон старше правки», считать из файла | В точности так деградирует `dataset_id`. Другой путь — заполнить колонку для старых прогонов задним числом — означал бы придумать им происхождение, которого мы не знаем. |
| История версий в SQLite, а не в `configs/*.json` | Файл отслеживается гитом, `configs/` смонтирован на запись. Приложение не должно делать рабочую копию грязной. |
| Уникальность через `COALESCE(kappa_dataset_id, 0)` | `UNIQUE` в SQLite считает NULL различными, и недоставленные строки плодились бы без ограничения. |
| Правило «присвоить строку с NULL» | Сохраняет существующую передачу `session_registry` → `KappaUploader`, на которую они оба опираются по докстрингу. |
| Миграция отказывается при конфликте, а не сливает | Клинические данные; выбор «какая строка верна» — не решение автоматики. |
| Восстановление 319 строк — отдельный скрипт | Зависит от конкретного дампа, одноразово, должно запускаться осознанно. |
