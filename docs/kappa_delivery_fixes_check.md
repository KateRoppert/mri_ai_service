# Проверка исправлений по отложенной выгрузке (итерация 2)

Проверяем ровно то, что чинили после первого круга тестов. Общий сценарный
чек-лист — в `docs/kappa_delivery_manual_check.md`; здесь только регрессии.

Проверено 28.09 перед началом: код в контейнере, воркер поднялся
(`Kappa delivery worker started (tick=60s)`), в базе 13 прогонов `done`,
ожидающих нет — **плашки над таблицей быть не должно**. Всё, что появится, —
результат ваших действий.

---

## Два правила, без которых проверка бессмысленна

**1. Своя выходная папка на каждый сценарий.** Загрузчик и счётчики читают
выходную папку целиком, а не список пациентов на входе. Два прогона в одну
папку — и второй покажет пациентов первого (именно так вышло «каппа 0 из 2»
при одном пациенте).

**2. Первым делом смотреть `{выходная_папка}/logs/kappa.log`.** Там построчно
написано, что произошло с выгрузкой этого запуска. Общий `service.log` —
только если в `kappa.log` ответа нет.

### Как «уронить» и «поднять» Kappa

```bash
# уронить
docker exec -u root mri_ai_service-web-1 \
  sh -c 'echo "127.0.0.1 kappa.nsu.ru" >> /etc/hosts'

# поднять
docker exec -u root mri_ai_service-web-1 \
  sh -c "grep -v 'kappa.nsu.ru' /etc/hosts > /tmp/h && cat /tmp/h > /etc/hosts"

# проверить, что сейчас
docker exec mri_ai_service-web-1 grep kappa /etc/hosts \
  && echo "^^ Kappa заглушена" || echo "Kappa доступна"
```

Заглушка переживает `docker compose restart`, но исчезает при `up --build`
и `down`.

### Окно наблюдения

```bash
watch -n 5 "sqlite3 -box /home/ubuntu/mri_ai_service/backend/data/brain_lesion.db \"
SELECT substr(run_id,1,8) AS run, status AS прогон,
       COALESCE(kappa_upload_status,'—') AS выгрузка,
       COALESCE(json_extract(kappa_upload_detail,'\\\$.delivered'),0) || '/' ||
       COALESCE(json_extract(kappa_upload_detail,'\\\$.total'),0) AS сколько,
       COALESCE(json_extract(kappa_upload_detail,'\\\$.reason'),'') AS причина,
       COALESCE(kappa_upload_next_attempt,'') AS следующая
FROM pipeline_runs ORDER BY created_at DESC LIMIT 6;\""
```

## A. Работа вообще без Kappa

**Было:** весь интерфейс за формой входа. Нет Kappa → нет вкладок → нельзя
запустить ничего. Отложенной выгрузке было нечего откладывать.

1. Заглушить Kappa. **Обновить страницу в браузере.**

   Ожидается: вкладки на месте. В шапке — «Без входа в Kappa» и кнопка
   «Войти». Над содержимым — жёлтая плашка с объяснением. Формы входа
   вместо интерфейса больше нет.

2. Нажать «Войти» → попробовать войти.

   Ожидается: вход не проходит (Kappa же лежит). Окно закрывается по
   крестику, интерфейс остаётся рабочим.

3. Запустить обработку на **новой выходной папке**, 1 пациент. Дождаться
   завершения.

   Ожидается: прогон проходит целиком. В истории, колонка «Kappa»:

   > `ожидает выгрузки · Kappa недоступна`

   **Не** `0 из 0` — это второе исправление: пока счётчики не посчитаны,
   система говорит «не знаю», а не «отправлять нечего».

4. Поднять Kappa. Войти в аккаунт.

   Ожидается: сообщение «Возобновлена выгрузка в Kappa: N запуск(ов)», и в
   течение минуты тег зеленеет. Номер пациенту закрепляется за датасетом
   именно сейчас — до входа он был выдан в области `pending:<run_id>`.

5. Открыть `{выходная_папка}/logs/kappa.log`.

   Ожидается примерно такое:

   ```
   Запуск начат. Датасет Kappa ещё не определён.
     Kappa недоступна: номера будут закреплены за датасетом при выгрузке
   Попытка (после прогона): пропущена — нет входа в Kappa
     Итог: ждёт — 0 из 0 (нет входа в Kappa)
   Попытка (фоновая досылка): сессий найдено 1
       sub-001_ses-001 — загружено (entity ...)
     Итог: доставлено — 1 из 1
   ```

## B. Возврат Kappa замечается сам

**Было:** отсрочка росла до 30–60 минут, и возврат сервиса никто не замечал.
Помогал только ручной сброс таймера.

1. **Войти** в Kappa. Затем заглушить её.
2. Запустить обработку на новой выходной папке. Дождаться завершения.
3. Дать двум-трём попыткам провалиться — по окну наблюдения видно, как
   растёт `следующая` (1 → 2 → 5 минут).
4. Поднять Kappa. **Больше ничего не делать**: не входить заново, не
   сбрасывать таймер, не нажимать «Повторить».

   Ожидается: в течение примерно минуты воркер сам замечает, что Kappa
   отвечает, снимает отсрочку и досылает. В `service.log`:

   ```
   Retrying N waiting run(s) now: Kappa снова отвечает
   ```

Проба — обычное TCP-соединение, без токена и без обращения к API. Срабатывает
**только на переходе** «лежала → отвечает», иначе она бы обнуляла отсрочки
каждую минуту и механизм повторов перестал бы существовать.

## C. Выход из аккаунта не обрывает досылку

**Было:** выход удалял сессию вместе с токеном — единственным, чем можно
авторизоваться. Данные ждали повторного входа.

1. Войти. Заглушить Kappa.
2. Запустить обработку на новой выходной папке, дождаться завершения
   (состояние `ожидает выгрузки`).
3. **Выйти из аккаунта** в интерфейсе.
4. Поднять Kappa. **Не входить.**

   Ожидается: данные всё равно уходят — в течение минуты-двух. Это и есть
   ответ на вопрос «почему нельзя дослать, если я вышла».

Состояние «нужен вход в Kappa» осталось для случая, когда токен действительно
истёк (примерно 7 дней) или прогон запускали вообще без входа. В этом
состоянии попытки **не тратятся**: ожидание входа не ошибка.

## D. Упавший прогон больше не висит в плашке

**Было:** прогон, упавший на этапе 05, оставался «ожидающим выгрузки». Плашка
его считала, а воркер брал только завершённые — значит убрать его было нечем.
Отсюда «ожидают 2» при одном запущенном и плашка, не исчезавшая после
успешной досылки.

Проще всего воспроизвести падение перезапуском — прогон не переживает
перезапуск сервиса и помечается упавшим:

1. Запустить обработку (любую, лучше подлиннее).
2. Пока она идёт: `docker compose restart web`
3. Дождаться, пока бэкенд поднимется, открыть историю.

   Ожидается: прогон помечен как упавший, в колонке «Kappa» — прочерк `—`,
   **плашки над таблицей нет**.

Проверить в базе, что фантомов не осталось:

```bash
sqlite3 backend/data/brain_lesion.db "
SELECT COUNT(*) FROM pipeline_runs
 WHERE status != 'completed' AND kappa_upload_status IS NOT NULL;"
```

Должен быть `0`.

## E. Вкладка валидации обновляется сама

**Было:** список грузился только при смене датасета и по кнопке «Обновить».
Данные, доехавшие фоном, просто не появлялись.

1. Во время сценария B или C, пока выгрузка ещё не завершилась, открыть
   вкладку **Валидация** и выбрать датасет, куда поедут данные.
2. Дождаться доставки, **ничего не нажимая**.

   Ожидается: новая сессия появляется в списке сама, в пределах 10–20 секунд
   после доставки. Без спиннера и без баннера ошибки поверх — фоновое
   обновление намеренно тихое.

## Что проверять не нужно

**Сценарий «нет файлов»** (папку удалили, выгружать нечего) — проверен
автоматически, сквозь настоящий `deliver_one`: статус `needs_attention`,
причина `missing_files`, повтор **не назначается**, в логе строка
`Итог: требует внимания — 0 из 0 (нет файлов)`. Руками его не поймать:
данные уходят быстрее, чем успеваешь удалить папку.

**`name_clash`** — чтобы подстроить, нужно ломать нумерацию в боевом
датасете. Закрыт юнит-тестами.

## Уборка

```bash
# снять заглушку Kappa — обязательно
docker exec -u root mri_ai_service-web-1 \
  sh -c "grep -v 'kappa.nsu.ru' /etc/hosts > /tmp/h && cat /tmp/h > /etc/hosts"
docker exec mri_ai_service-web-1 grep kappa /etc/hosts || echo "заглушки нет — хорошо"
```

Тестовые прогоны останутся в истории обычными записями — удалять их не нужно,
они не мешают ни плашке, ни воркеру.
