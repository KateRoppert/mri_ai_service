# Отложенная выгрузка в Kappa — ручная проверка

Чек-лист для проверки живьём: что видит оператор, когда Kappa недоступна,
когда истёк токен и когда повтор уже не поможет.

Спека: `docs/superpowers/specs/2026-09-23-deferred-kappa-upload-design.md`

---

## Главное правило: своя выходная папка на каждый сценарий

Загрузчик и счётчики смотрят на **выходную папку**, а не на то, каких
пациентов вы выбрали на входе (`kappa_uploader._discover_sessions` сканирует
`preprocessed/` и `segmentation/` целиком). Если два прогона пишут в одну
папку, второй увидит и пациентов первого.

Именно это дало «каппа 0 из 2» при одном запущенном пациенте и двух
пациентов на главной вкладке: четыре прогона 25.09 писали в
`demo_workspace/input/25_09_1602`. Счётчик не врал — он честно описывал, что
уйдёт в Kappa.

**Для каждого сценария указывайте новую выходную папку.** Иначе вы будете
проверять не то, что думаете.

---

## Где смотреть, что произошло

У каждого запуска теперь свой лог выгрузки — `{выходная_папка}/logs/kappa.log`:

```
2026-09-25 16:02:11  Запуск начат. Датасет Kappa: 351.
2026-09-25 16:04:34  Попытка (после прогона): сессий найдено 1
2026-09-25 16:04:34      sub-001_ses-001 — не отправлено: Kappa не приняла файлы
2026-09-25 16:04:34    Итог: ждёт — 0 из 1 (Kappa недоступна), следующая попытка 16:05:34
2026-09-25 16:09:42  Попытка (фоновая досылка): сессий найдено 1
2026-09-25 16:09:42      sub-001_ses-001 — загружено (entity 105af2a5)
2026-09-25 16:09:42    Итог: доставлено — 1 из 1
```

Если что-то ведёт себя непонятно — сначала сюда, а не в общий `service.log`.

## 0. Подготовка

### Пересобрать образ — обязательно

`backend/` и `frontend/` **запечены в образ**, а не смонтированы. Рестарт
контейнера новый код не подхватит.

```bash
cd /home/ubuntu/mri_ai_service
docker compose --profile full up --build -d
```

### Убедиться, что миграция прошла

```bash
sqlite3 backend/data/brain_lesion.db "PRAGMA table_info(pipeline_runs);" | grep kappa_upload
```

Ожидается три строки: `kappa_upload_status`, `kappa_upload_next_attempt`,
`kappa_upload_detail`.

### Окно наблюдения

В отдельном терминале — состояние выгрузки по последним прогонам. Воркер
просыпается раз в 60 секунд, так что обновление раз в 5 секунд ловит всё:

```bash
cd /home/ubuntu/mri_ai_service
watch -n 5 "sqlite3 -box backend/data/brain_lesion.db \"
SELECT substr(run_id,1,8) AS run,
       COALESCE(kappa_upload_status,'—') AS выгрузка,
       COALESCE(json_extract(kappa_upload_detail,'\\\$.delivered'),0) || '/' ||
       COALESCE(json_extract(kappa_upload_detail,'\\\$.total'),0) AS сколько,
       COALESCE(json_extract(kappa_upload_detail,'\\\$.reason'),'') AS причина,
       COALESCE(json_extract(kappa_upload_detail,'\\\$.attempts'),0) AS попыток,
       COALESCE(kappa_upload_next_attempt,'') AS следующая
FROM pipeline_runs ORDER BY created_at DESC LIMIT 8;\""
```

И логи воркера в третьем терминале:

```bash
tail -f logs/service.log | grep -Ei "deferred delivery|kappa delivery|delivery worker"
```

При старте бэкенда в логе должно появиться `Kappa delivery worker started (tick=60s)`.
Если этой строки нет — воркер не поднялся, и всё остальное проверять бессмысленно.

## 1а. Работа вообще без Kappa

Раньше это было невозможно: весь интерфейс прятался за формой входа.

1. Заглушить Kappa (команда из 1.1 ниже), затем **перезагрузить страницу**.

**Ожидается:** вкладки на месте, в шапке «Без входа в Kappa» и кнопка
«Войти», над содержимым — жёлтая плашка с объяснением. Вход не проходит, и
это нормально.

2. Запустить обработку на новой выходной папке. Она должна пройти целиком.
3. Снять заглушку и войти в Kappa.

**Ожидается:** сообщение «Возобновлена выгрузка в Kappa: N запуск(ов)», и в
течение минуты данные уходят. Номера пациентов закрепляются за датасетом
именно на этом шаге — до входа они выданы в области `pending:<run_id>`.

## 1. Kappa недоступна → досылка сама → done

Главный сценарий. Тот, ради которого всё делалось.

### 1.1 «Уронить» Kappa

Kappa живёт на `kappa.nsu.ru`. Подменяем ей адрес внутри контейнера — это
мгновенно, обратимо и не трогает ни сеть хоста, ни конфиги:

```bash
docker exec -u root mri_ai_service-web-1 \
  sh -c 'echo "127.0.0.1 kappa.nsu.ru" >> /etc/hosts'
```

Проверить, что подействовало:

```bash
docker exec mri_ai_service-web-1 python -c "
import socket
try:
    socket.create_connection(('kappa.nsu.ru', 8061), timeout=5).close()
    print('всё ещё отвечает — заглушка не сработала')
except Exception as e:
    print('недоступна:', type(e).__name__)
"
```

(Проверяем именно TCP-соединение: доходит ли трафик до хоста. Сертификаты
тут ни при чём, и трогать их проверку не нужно.)

Ожидается `недоступна: ConnectionRefusedError` — имя теперь резолвится
в localhost, где на порту 8061 никто не слушает.

> Важно: войти в Kappa через интерфейс нужно **до** этого шага — иначе
> не будет сессии, и получится сценарий 2, а не этот.

### 1.2 Запустить небольшой прогон

Через интерфейс, на 1–3 пациентах (например, KA01).

**Что должно быть видно:**

| Где | Что |
|---|---|
| Экран прогресса, сразу после завершения | Жёлтое предупреждение «Результаты пока не ушли в Kappa. Досылка выполняется автоматически, данные не потеряны.» |
| История запусков, колонка «Kappa» | Жёлтый тег вида `0 из 3 в Kappa · досылка, когда сервис будет доступен` |
| Над таблицей истории | Жёлтая плашка «Ожидают выгрузки в Kappa: N» |
| Окно наблюдения | `pending`, причина `network`, попыток растёт |

Паузы между попытками: **1 → 2 → 5 → 15 → 30 → 60 минут**. То есть вторая
попытка через минуту, третья через две и так далее. Если ждать лень —
переходите к 1.3 сразу, воркер подхватит по наступлении времени.

### 1.3 Поднять Kappa обратно

```bash
docker exec -u root mri_ai_service-web-1 \
  sh -c "grep -v 'kappa.nsu.ru' /etc/hosts > /tmp/h && cat /tmp/h > /etc/hosts"
```

Ждать и сбрасывать таймер вручную больше не нужно: воркер сам проверяет
доступность Kappa (обычным TCP-соединением) и, увидев, что она вернулась,
снимает отсрочку со всех ждущих прогонов. Должно сработать в пределах минуты.

Если всё же хочется поторопить — можно сбросить таймер руками. Обратите
внимание на `run_id`: без него команда тронет **все** ждущие прогоны, а
не тот, который вы проверяете.

```bash
sqlite3 backend/data/brain_lesion.db \
  "UPDATE pipeline_runs SET kappa_upload_next_attempt = NULL
    WHERE run_id = '<ваш run_id>';"
```

**Что должно произойти:**

- в логе: `Deferred delivery <run>: done (3/3, reason=None)`
- тег в истории зеленеет: `Kappa 3/3`
- плашка над таблицей исчезает
- **в датасете Kappa каждый пациент ровно один раз** — это и надо проверить
  глазами, ради этого весь механизм дедупликации

## 2. Выход из аккаунта не обрывает досылку

Поведение изменено: выход закрывает сеанс в браузере, но токен живёт до
своего естественного истечения, и досылка продолжается сама.

1. Войти в Kappa, запустить прогон **на новой выходной папке**.
2. Пока прогон идёт — выйти из Kappa в интерфейсе.
3. Дождаться завершения.

**Ожидается:** данные уходят в Kappa **без повторного входа**. Это и был
ответ на вопрос «почему нельзя дослать, если я вышла» — раньше выход стирал
единственный ключ, теперь нет.

Состояние `нет входа в Kappa` остаётся для случая, когда токен действительно
истёк (примерно через 7 дней) или прогон запускали вообще без входа. Тогда
попытки **не тратятся** — ожидание входа не считается ошибкой, — а сам вход
сразу возобновляет выгрузку.

---

## 3. Файлов нет → нужна проверка человека

Повтор такое не чинит, поэтому система обязана перестать пытаться.

1. Взять завершённый прогон, которому ещё есть что досылать.
2. Переименовать его выходную папку:

```bash
mv /путь/к/output /путь/к/output_backup
```

3. Нажать на тег в истории → **«Повторить сейчас»**.

**Ожидается:** статус `needs_attention`, причина `missing_files`, красный
тег, **следующая попытка не назначается** (столбец `следующая` пустой).

4. Вернуть папку обратно: `mv /путь/к/output_backup /путь/к/output`

## 4. Долгий отказ → «не удаётся выгрузить»

Правило `stuck`: сутки повторов без единой доставленной сессии — и прогон
уходит к человеку. Ждать сутки не нужно, достаточно сдвинуть точку отсчёта.

1. Оставить прогон в `pending` с причиной `network` (сценарий 1, Kappa лежит).
2. Состарить первую неудачу на 25 часов:

```bash
sqlite3 backend/data/brain_lesion.db "
UPDATE pipeline_runs
   SET kappa_upload_detail = json_set(
         kappa_upload_detail, '\$.first_failure_at',
         strftime('%Y-%m-%dT%H:%M:%S+00:00', 'now', '-25 hours')),
       kappa_upload_next_attempt = NULL
 WHERE kappa_upload_status = 'pending';"
```

**Ожидается** на следующем тике: `needs_attention`, причина `stuck`, тег
`0 из N · не удаётся выгрузить`, повторы прекращаются.

Это единственный путь, которым отказ в правах или удалённый датасет
доходят до человека — коды ответа Kappa до нас не доходят, их гасит
`kappa_client`.

---

## 5. Чего проверить не получится руками

**`name_clash`** — когда один и тот же `sub-NNN` выдан дважды в один
датасет разным пациентам. Чтобы это подстроить, нужно ломать нумерацию в
боевом датасете — перед проверкой так делать не стоит. Путь закрыт
юнит-тестами (`backend/test_kappa_delivery.py`), а как это выглядит в
интерфейсе, видно на «поддельной» строке из раздела 6.

## 6. Уборка после тестов

База приведена в порядок 24.09 перед началом проверки: синтетические
строки `ui_kappa_*` удалены, у трёх прогонов сняты устаревшие признаки
отказа. На старте проверки все отслеживаемые прогоны — `done`, плашки над
таблицей нет. Всё, что появится дальше, — результат ваших действий.

Если по ходу тестов появятся свои поддельные строки, убрать их так:

```bash
sqlite3 backend/data/brain_lesion.db "
DELETE FROM stage_executions WHERE run_id LIKE 'ui_kappa%';
DELETE FROM pipeline_runs   WHERE run_id LIKE 'ui_kappa%';"
```

**Обязательно проверить, что заглушка Kappa снята** — иначе следующий
реальный прогон молча не дойдёт до Kappa:

```bash
docker exec mri_ai_service-web-1 grep kappa /etc/hosts || echo "заглушки нет — хорошо"
```

Резервная копия базы перед уборкой лежит рядом:
`backend/data/brain_lesion.db.bak-20260924-160707`

## Подводный камень

Поддельные строки в `pipeline_runs` со статусом `pending` **не лежат
спокойно**: воркер подхватывает их как настоящие, не находит файлов на
диске и переводит в `needs_attention/missing_files`. Именно так строка,
заведённая как «pending», оказалась в базе с `needs_attention`. Чтобы
посмотреть на вид `pending` в интерфейсе, ставьте таким строкам
`kappa_upload_next_attempt` далеко в будущее — тогда воркер их не тронет.
