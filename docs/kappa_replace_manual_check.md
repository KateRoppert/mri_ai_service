# Замена переобработанного пациента в Kappa — ручная проверка

Ветка `feat/kappa-replace-on-reprocess`. Нужна пересборка образа: изменения
в `backend/` не монтируются живьём.

```bash
docker compose --profile full up --build -d
```

## Что должно было измениться

До этой доработки переобработка пациента, уже выгруженного в Kappa, была
тихо бесполезной: `study_hash` считается от `PatientID:StudyInstanceUID` —
то есть от DICOM-исследования, а не от картинок. Пересчёт с исправленным
набором модальностей даёт **тот же хэш**, выгрузка считала пациента
дубликатом и писала «доставлено». Локально исправлено, в Kappa — старое, и
никто об этом не сообщал.

Теперь такая сессия помечается как вытесняющая, прогон уходит в
«требует внимания», и в модалке появляется кнопка замены с подтверждением.

## Подготовка

Проверь, что миграция прошла:

```bash
sqlite3 backend/data/brain_lesion.db "PRAGMA table_info(pipeline_runs);" \
  | grep reprocessed_sessions
```

Ожидается одна строка. Если пусто — контейнер не перезапустился с новым кодом.

Токен для прямых запросов в Kappa (понадобится, чтобы смотреть сущность
глазами, а не через наш интерфейс):

```bash
sqlite3 backend/data/brain_lesion.db \
  "SELECT kappa_token FROM kappa_sessions ORDER BY created_at DESC LIMIT 1;"
```

## Сценарий A — основной путь

1. Возьми пациента, который **уже выгружен** в Kappa (в истории у прогона
   зелёный статус выгрузки).
2. Запомни, как сущность выглядит сейчас:

```bash
TOKEN=<токен>
DS=<kappa_dataset_id прогона>
curl -sk -H "Authorization: Bearer $TOKEN" \
  "https://kappa.nsu.ru:8061/data-micro-services/v2/datasets/datasetEntities/$DS" \
  | python3 -m json.tool | grep -E 'dsEntityName|fileName|fileId'
```

Выпиши **число файлов и их fileId** для своего пациента. Это главный
измеритель всей проверки.

3. Открой пациента в очереди неполных, поменяй набор модальностей
   (например, сними t2fl и назначь на неё другую серию), сохрани.
4. Нажми «Запустить обработку заново» и дай прогону завершиться.

**Ожидается:**
- прогон заканчивается со статусом выгрузки **«требует внимания»**;
- в колонке Kappa подпись **«в Kappa прежняя версия»**;
- в модалке прогона в списке «Требуют внимания» есть строка с этой сессией и
  кнопка **«Заменить в Kappa»**;
- в `{output}/logs/kappa.log` строка вида
  `sub-NNN_ses-NNN — не отправлено: в Kappa прежняя версия — нужно подтвердить замену`.

5. Нажми «Заменить в Kappa». Прочитай текст подтверждения — он должен прямо
   говорить, что прежняя версия не сохранится.
6. Подтверди.

**Ожидается:** сообщение вида «Заменено файлов: N, добавлено 0, удалено 0».

7. Повтори запрос из пункта 2.

**Ожидается — это и есть суть проверки:**
- **число файлов НЕ выросло**;
- **fileId те же самые**, что ты выписала (v2 PATCH заменяет на месте,
  сохраняя id — в отличие от v1, который добавлял второй файл с тем же именем);
- содержимое новое (можно скачать и сверить размер/дату).

## Сценарий B — экспертные маски переживают замену

Если у пациента есть экспертные правки масок (`*_segmask_v2.nii.gz` и т.д.):

1. Перед заменой убедись, что они есть в сущности (видно в выводе пункта 2).
2. В подтверждении должна появиться дополнительная строка: «У пациента есть
   экспертные маски (N). Они останутся, но нарисованы по прежним данным».
3. После замены проверь, что все `_segmask_v*` на месте.

**Это главный риск всей фичи.** Экспертная маска — отдельное мнение
специалиста, а не исправление ошибки, и она не входит в пересчитываемый
набор. Без исключения из правила «чего нет в новом наборе — удалить» первая
же замена стёрла бы всю работу эксперта.

## Сценарий C — замену нельзя вызвать для чего угодно

Эндпоинт перезаписывает данные в чужой системе, поэтому он обязан отказывать
любой сессии, которую этот прогон не переобрабатывал:

```bash
curl -sk -X POST \
  "http://localhost:8000/api/kappa/replace-entity/<run_id>/sub-999/ses-001?kappa_session_id=<id>"
```

**Ожидается:** `400` и текст «не помечена как вытесняющая — заменять нечего».

## Сценарий D — набор поменяли, но пациента в Kappa ещё нет

1. Возьми пациента, которого в Kappa **не** выгружали.
2. Поменяй набор, переобработай.

**Ожидается:** обычная выгрузка, статус «доставлено», никакой кнопки замены.
Вытеснять нечего — пациент попадает в датасет впервые.

## Сценарий E — регрессия: обычный прогон не изменился

Запусти обработку нового пациента без всякой переобработки.

**Ожидается:** всё как раньше — «доставлено», ни «требует внимания», ни
кнопки замены. Если здесь что-то поменялось, значит условие вытеснения
срабатывает шире, чем должно.

## Если замена прошла частично

Сообщение скажет, какие файлы не удалось заменить, и что действие можно
повторить. Повтор безопасен: замена идемпотентна — совпадающие имена
заменяются на месте, лишнего не добавляется.

Отдельный случай — «Удаление лишних ещё идёт в Kappa». Удаление в v2
асинхронное (сервер отдаёт `jobId`), мы опрашиваем его до 60 секунд. Если не
дождались, сервис честно говорит «ещё идёт», а не «готово»: утверждать исход,
которого мы не видели, нельзя. Проверь сущность через минуту.

## Что сообщить

По каждому сценарию: что ожидалось, что увидела. Для сценария A обязательно
число файлов и fileId до и после — остальное без них не доказательство.
