# Предыдущая статья (IEEE EDM 2026)

«Profiling a Brain MRI Pipeline for Multi-Agent Resource Allocation» — профилирование
шестиэтапного пайплайна на UPENN-GBM и симуляция четырёх стратегий распределения.
Настоящее исследование (`docs/superpowers/specs/2026-10-23-mas-resource-negotiation-design.md`)
является её продолжением: там, где эта статья предложила архитектуру и проверила её
симуляцией, следующая реализует прототип и меряет его вживую.

## Железо прошлой статьи

- **CPU-эксперименты (этапы 1–5):** Intel Core i7-13700KF (16 ядер / 24 потока),
  **64 ГБ DDR5**, NVMe SSD, Ubuntu 24.04. Параллелизм варьировался от 1 до 20 процессов.
- **GPU-эксперименты (этап 6):** Server A — 2×RTX A4500 (20 ГБ VRAM каждая);
  Server B — Quadro RTX 8000 (48 ГБ); Server C — GTX TITAN X (12 ГБ).

Статья не говорит, является ли CPU-станция тем же физическим хостом, что Server A.
Для Блока 0 нового исследования это нужно установить: 64 ГБ RAM против лимита
контейнера 20 ГБ — разные режимы работы планировщика памяти.

## Данные

UPENN-GBM, 100 пациентов → 110 сессий, 4 модальности. Не во всех сессиях полный
набор: 103 сессии содержат референсный T1 для этапа 5, 98 — все четыре модальности
для сегментации. **Объёмы глиобластомы 10–78 Мвокс** (для сравнения: SibBMS — до
231 Мвокс, см. KI-042).

## Протокол замеров

Перед каждым прогоном дисковый кэш сбрасывался (`sync` + `echo 3 >
/proc/sys/vm/drop_caches`, 2 с стабилизации). Без сброса I/O-этапы показывали
ускорение завышенным в 2–4 раза. Этапы 1–3 прогонялись дважды (разброс <10%),
этапы 4–5 — один раз (>2 ч на конфигурацию).

Выводы статьи: перекрытие этапов важнее глубины параллелизма внутри этапа
(3.26× против 2.29×); динамическая переаллокация закрывает разрыв по утилизации
(4.7×, +44% к Pipeline); выигрыш растёт с размером партии (19% на 20 пациентах,
31% на 100); МАС устойчива к накладным расходам переговоров — при росте с 1 с до
10 с на цикл makespan идёт с 22.6 до 25.6 мин, всё ещё на 21% быстрее Pipeline.

Из Limitations: **в режиме МАС сегментация занимает ~80% makespan** — то есть
узкое место смещается на GPU. Это прямо означает, что на машине с одной картой
выигрыш МАС будет меньше, и что матрицу надо гонять там, где карт столько же,
сколько в симуляции.

## Три расхождения с текущим состоянием кода

Это не ошибки статьи, а то, что изменилось или уточнилось после её выхода.
Каждое влияет на дизайн нового исследования.

### 1. «Память не является ограничением» — верно только для этого датасета и этого способа замера

Статья: «peak RAM consumption dropped from 1.7 GB at w=1 to 338 MB at w≥2,
indicating that saturation is driven by CPU contention rather than memory
exhaustion» (этап 5).

Что выяснилось позже в проекте:

- **Зависит от данных.** На UPENN-GBM объёмы 10–78 Мвокс; на SibBMS — 231 Мвокс,
  и там этап 05 упирается именно в память: измеренный пик 8.0–8.6 ГБ на воркер,
  cgroup OOM, в одном случае global OOM снёс рабочий стол (KI-042, KI-043, KI-058).
- **Зависит от метода.** Пик мерили сэмплированием RSS, которое его занижает;
  в проекте перешли на точный `VmHWM` через `/proc/self/clear_refs` (KI-058,
  обновление 12.10.2026) — после этого «прошедшие» прогоны оказались на грани.
  Падение пика с 1.7 ГБ до 338 МБ при добавлении воркеров — скорее артефакт
  сэмплирования, чем физика.

**Следствие для нового исследования:** RQ5a должен проверять не только совпадение
точек насыщения между датасетами, но и **смену связывающего ресурса** (ядра против
памяти). P0 перемеряет профили с `VmHWM`, и новые числа разойдутся со старыми —
это стоит заявить как методологическую поправку, а не умолчать.

### 2. Убеждение продакшн-кода про этап 05 противоречит измеренному профилю

Статья измерила насыщение этапа 5 на **6 процессах** (24-поточная станция).
Текущий код считает `workers_by_cpu = (os.cpu_count() − 2) // 8`, то есть на
24 потоках даёт **2 воркера** ([`05_preprocessing.py`](../../../scripts/05_preprocessing.py)),
исходя из «8 ядер на воркер ANTs/FSL». На данных глиобластомы память столько
разрешает (78 Мвокс × 25 Б/воксель ≈ 1.95 ГБ на воркер, бюджет 15 ГБ → 7),
значит связывает именно эвристика `//8`.

**Следствие:** «статический бейзлайн» и «то, как работает сейчас» — это не одно и
то же, и P0 обязан разобрать, 6 или 2 правильнее и при каком числе потоков на
воркер. Возможно, часть выигрыша МАС на этапе 05 доступна простым исправлением
одной константы — и это надо знать до того, как приписать её агентности.

### 3. Прототип был публично обещан на SPADE

Future work статьи: «a prototype MAS will be implemented using the **SPADE** agent
framework within the existing FastAPI/Docker infrastructure». Текущий план (3.6)
описывает агентов как корутины одного asyncio-процесса, без SPADE.

**Следствие:** либо SPADE, либо в новой статье нужно явное обоснование отклонения
(общая память → переговоры близки к нулю; SPADE с XMPP добавил бы транспорт,
которого на одном узле не требуется). Рецензент, знакомый с первой статьёй,
спросит.
