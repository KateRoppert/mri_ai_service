# Очередь повторного запуска — ручная проверка

Ветка `feat/queued-requeue`. Нужна пересборка образа: `backend/` в контейнер
не монтируется.

```bash
docker compose --profile full up --build -d
sqlite3 backend/data/brain_lesion.db "PRAGMA table_info(pipeline_runs);" \
  | grep queued_requeue_at
```

Вторая команда должна вернуть строку. Если пусто — контейнер не поднялся с
новым кодом.

## Что изменилось

Раньше кнопка «Запустить обработку» в модалке неполных пациентов гасла, пока
идёт прогон, и предлагала дождаться завершения. Теперь она доступна всегда:
пока путь занят, запуск встаёт в очередь и стартует сам.

Два процесса orchestrator над одним `dataset_mapping.json` по-прежнему
невозможны — раньше времени ничего не начинается.

## Сценарий A — основной путь

1. Запусти обработку датасета, где есть неполные пациенты.
2. **Не дожидаясь завершения**, открой модалку неполных пациентов.

Ожидается: кнопка **активна** и подписана «Поставить в очередь».

3. Нажми её. В подтверждении должно быть сказано, что запуск встанет в
   очередь и начнётся после завершения текущей обработки.
4. Подтверди.

Ожидается: синее сообщение «Запуск поставлен в очередь», модалка **не
закрывается**, сверху появляется плашка «Запуск в очереди» с кнопкой
«Отменить».

5. Обнови страницу браузера и снова открой модалку.

Ожидается: плашка «Запуск в очереди» **на месте**. Это главная проверка
того, что состояние живёт на сервере, а не в одной вкладке.

6. Дождись завершения текущего прогона.

Ожидается: новый прогон стартует **сам**, без твоего участия. В истории
появляется строка с `parent_run_id` предыдущего прогона.

Проверить по логу контейнера:

```bash
docker logs mri_ai_service-web-1 2>&1 | grep -E "в очередь|освободился"
```

Должны быть две строки: «Requeue поставлен в очередь на …» и «Путь … 
освободился — запускаем отложенный прогон».

## Сценарий B — отмена

1. Поставь запуск в очередь, как в сценарии A.
2. Нажми «Отменить» на плашке.

Ожидается: «Запуск снят с очереди», плашка исчезает.

3. Дождись завершения текущего прогона.

Ожидается: новый прогон **не** стартует.

## Сценарий C — правка, сделанная во время ожидания

Это проверка того, ради чего задача устроена именно так.

1. Запусти обработку. Пока она идёт, открой неполных пациентов, поправь
   набор модальностей **одному** пациенту и поставь запуск в очередь.
2. Пока прогон ещё идёт, поправь набор **второму** пациенту.
3. Дождись автоматического старта.

Ожидается: переобработаны **оба** пациента, а не только первый. И если
кто-то из них уже был выгружен в Kappa — он попадает в список на замену
(статус «требует внимания», подпись «в Kappa прежняя версия»).

Проверить, что в очередь попали оба:

```bash
sqlite3 backend/data/brain_lesion.db \
  "SELECT substr(run_id,1,8), reprocessed_sessions FROM pipeline_runs
   ORDER BY created_at DESC LIMIT 1;"
```

Ожидается: в `reprocessed_sessions` **две** сессии. Если там одна — значит
список снялся в момент клика, а не при старте, и второй пациент тихо
остался бы в Kappa со старой версией.

## Сценарий D — повторный клик

1. Поставь запуск в очередь. Нажми кнопку ещё раз и подтверди.

Ожидается: та же плашка, никакой ошибки. Очередь одна на путь — второй
прогон подряд всё равно нашёл бы все результаты готовыми и просто пропустил
их.

## Сценарий E — путь свободен (регрессия)

1. Дождись завершения всех прогонов. Открой неполных пациентов.

Ожидается: кнопка подписана **«Запустить обработку»** (не «Поставить в
очередь»), обработка начинается сразу, плашки очереди нет.

2. Отдельно проверь **остановленный** прогон: останови обработку и открой
   его модалку.

Ожидается: тоже «Запустить обработку» — остановленный прогон путь не
занимает. Если здесь написано «Поставить в очередь», значит занятость пути
определяется по статусу прогона вместо самого пути.

## Сценарий F1 — прогон упал, бэкенд жив

Это **не** то же самое, что перезапуск контейнера: там срабатывает другой
путь (F2). Нужно, чтобы упал именно прогон, а сервис продолжал работать.

1. Запусти обработку и поставь ещё один запуск в очередь.
2. Убей процесс пайплайна, не трогая сервис:

```bash
docker exec mri_ai_service-web-1 pkill -f orchestrator.py
```

Ожидается: прогон получает статус `failed`, отложенный запуск **не**
стартует, в логе строка «Запуск из очереди на … отменён: прогон …
завершился со статусом failed».

```bash
docker logs mri_ai_service-web-1 2>&1 | grep "из очереди"
```

Почему так: автостарт после падения спрятал бы само падение, а на сломанном
окружении дал бы цикл «упал — перезапустился — упал». Твоя правка при этом
не теряется — она на диске, следующий запуск её подхватит.

## Сценарий F2 — перезапуск бэкенда

1. Поставь запуск в очередь и перезапусти контейнер web.

Ожидается: интерфейс сообщает о потере соединения, после подъёма плашки
очереди нет и ничего не возобновляется. В логе при старте:

```bash
docker logs mri_ai_service-web-1 2>&1 | grep -E "Сняты с очереди|осиротевш"
```

Должны быть обе строки — «осиротевших прогонов помечены failed» и «Сняты с
очереди N запуск(ов)». Если второй нет, значит очередь была пуста и сценарий
ничего не проверил.

Автостарт после краха небезопасен: orchestrator мог умереть посреди записи
`dataset_mapping.json`.

## Сценарий G — возобновление остановленного прогона (повторно)

Это проверка исправления той заморозки, которую ты поймала 09.10. Нужна
пересборка после коммита `badb7ac`.

1. Запусти обработку, дождись этапа 2-3 и останови её.
2. Возобнови («Возобновить» в истории или в мониторе прогресса).
3. **Сразу же**, не дожидаясь ничего, обнови страницу истории и открой любую
   другую вкладку сервиса.

Ожидается: интерфейс отвечает как обычно, прогресс по новому прогону идёт в
реальном времени. Раньше бэкенд замирал на всё время прогона: API не
отвечал, прогресс не обновлялся, в логе контейнера после строки «Порог
простоя для run_id …» не появлялось **ничего** до самого конца.

Быстрая проверка из терминала, пока прогон идёт:

```bash
curl -sS --max-time 5 -o /dev/null -w "HTTP %{http_code}, %{time_total}s\n" "http://localhost:8000/api/pipeline/history?limit=1"
```

`--max-time 5` обязателен: без него curl ждёт ответа **вечно** и не печатает
ничего — а именно так выглядит заморозка, которую мы проверяем. Проверка,
которая сама зависает, ничего не сообщает.

Как читать результат:

| Вывод | Что это значит |
|---|---|
| `HTTP 200` за доли секунды | Всё хорошо |
| `HTTP 000` + `Operation timed out` | Бэкенд не отвечает — заморозка |
| `HTTP 000` + `Could not connect` | Контейнер не поднят |

4. То же самое проверь для запуска **из очереди** (сценарий A): пока
   отложенный прогон идёт, интерфейс должен отвечать.

## Что сообщить

По каждому сценарию: что ожидалось, что увидела. Для сценария C обязательно
содержимое `reprocessed_sessions` — остальное без него не доказательство.
