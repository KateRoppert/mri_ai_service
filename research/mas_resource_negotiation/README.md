## P0: профиль насыщения этапа

Развёртка гоняет `orchestrator.py` с сгенерированным конфигом, в котором включён
ровно один этап. На каждую клетку копируется подготовленное дерево, так что все
клетки начинают с побайтно равных данных; собственный `skip-existing` этапа
выключается, иначе вторая клетка «пропустит» готовую работу и окажется
мгновенной.

**Подготовка.** Нужно дерево с выходом предыдущих этапов — вход профилируемого.
Например для этапа 05 это каталог прогона, в котором уже есть `nifti/`. Проще
всего взять готовый прогон и скопировать из него нужные подкаталоги.

**Запуск.**

```bash
source venv/bin/activate

# сброс кэша требует прав: без sudo он не сработает, и это попадёт в артефакт
sudo -E env "PATH=$PATH" python research/mas_resource_negotiation/sweep_stage.py \
    --stage stage_05_preprocessing \
    --workers 1 2 4 6 8 12 \
    --repeats 3 \
    --work-dir /путь/к/подготовленному/дереву \
    --out research_results/p0_stage05

# прервалось — тот же вызов дочитает недостающие клетки
# только таблица по уже посчитанному:
python research/mas_resource_negotiation/sweep_stage.py \
    --out research_results/p0_stage05 --summary
```

**Что получится** в каталоге результатов:

* `results.jsonl` — по строке на клетку: время, сделанные сессии, утилизация
  дерева процессов и машины, пик памяти, iowait, диск, энергия GPU и CPU,
  распределение времени ожидания, и сбрасывался ли кэш;
* `environment.json` — машина и версии: модель процессора, карты, драйвер,
  antspyx, коммит кода и грязное ли дерево. Без него числа не значат ничего
  (контроль Блока 0);
* `config_*.yaml` и `work_*/` — конфиг и дерево каждой клетки, чтобы прогон
  можно было повторить вручную.

**Точка насыщения** считается как в прошлой статье: наименьшее число процессов,
после которого прирост пропускной способности меньше 5%.

## Что проверить на баргузине до первого прогона

1. **Миграция нумерации** — см. gotchas в `CLAUDE.md`. Сухой прогон
   `python scripts/migrate_bids_allocation_scopes.py` отвечает за секунду.
2. **Права на RAPL**, иначе энергия CPU не соберётся (`cpu_energy_wh: null`):
   `cat /sys/class/powercap/intel-rapl:0/energy_uj` должен читаться без sudo.
   Как открыть — в журнале решений спеки, запись от 05.11.2026.
3. **Лимит памяти контейнера** задать от RAM машины, а не константой `20g`
   (KI-058): на машине с меньшей памятью он не защищает хост.
4. **`exclude_gpus`** в `configs/preprocessing_config.yaml` — на станции
   дисплейную карту исключать, на одногпушной машине оставлять пустым.

## Оговорки, которые надо унести в статью

* Протокол сбрасывает дисковый кэш перед каждой клеткой. В продакшене
  страничный кэш работает, поэтому для I/O-этапов замер **намеренно
  пессимистичен**.
* Регистрация воспроизводима только при одном потоке (KI-080), поэтому
  клинические выходы разных клеток сравнивать нельзя — время можно.
* На простое машина тратит ~24 Вт, так что «энергия до результата» выгоднее
  быстрым стратегиям сильнее, чем следует из одной мощности.
